# Agent 项目合格性审查

判定标准基于《一个好的 agent 项目的特征》7 节 + 11 条清单（原文摘要见 [references/rubric.md](references/rubric.md)）。

**这套标准的重心不是"多聪明"，而是"能不能可控地完成任务"。** 一句话判据：

> 如果一个项目只有 Prompt 和调用链，没有工程系统，面试官很容易判断它只是 Demo。

所以本技能的默认倾向是**偏严**：没有证据的机制一律按"缺失"处理，不按 README 的自我描述算分。

## 三种模式

| 模式 | 触发 | 做什么 |
|---|---|---|
| **Audit（默认）** | `/agent-project-review` | 全量审查：7 支柱 + 11 条清单，逐条判定 + 证据 + 档位结论 + 行动清单 |
| **Quick** | `/agent-project-review quick` 或「先看够不够格」 | 只跑 30 秒 Demo 过滤器 + 3 条否决项，直接给"能不能写简历"的初判 |
| **Compare** | `/agent-project-review compare` | 两个及以上项目并排，找互补与真空区，判断能否凑成一套完整答卷 |

审查前先读 [references/rubric.md](references/rubric.md) 对齐口径；需要动手核实时读 [references/evidence-commands.md](references/evidence-commands.md)；产出报告时套用 [references/report-template.md](references/report-template.md)。

## 输入与事实边界

1. **优先本地读代码**：仓库路径、README、设计文档、评测脚本、CI 配置。能实测的一律实测。
2. **没有代码就降级**：只能基于描述给"待确认"判定，并在报告开头声明本次是**文本审查**，不是实测审查。
3. **不替项目补分**：README 声称"支持多轮会话"但代码里没有会话表 → 判"缺"，并注明矛盾。
4. **区分"有"和"强"**：`logging` 命中 1 次 ≠ 有可观测性体系。判定必须写出计数或文件位置。
5. **不编造**：拿不到的运行时结论（真实 QPS、线上准确率）只写"未验证"，不推测数值。

## 一、30 秒 Demo 过滤器（Quick 模式全部内容）

任一命中 → 直接初判为 **Demo**，后续审查只在报告里解释原因：

| # | 现象 | 否定的是 |
|---|---|---|
| 1 | 仓库里能看的只有 Prompt 文本 + 一个调用脚本，没有服务层 | 第 2 条 后端工程 |
| 2 | 没有任何持久化（无 DB / 无表 / 无会话存储，刷新即失忆） | 第 3 条 持久化 |
| 3 | 全仓库 `logger` / `logging` 命中 ≈ 0，出错只有 `print` | 第 7 条 可观测性 |
| 4 | 工具调用是硬编码 if/else 或写死的链，没有工具契约与选择逻辑 | 第 5 条 Agent 能力 |
| 5 | Prompt 里塞入全部历史对话，没有裁剪 / 摘要 / 分层 | 第 4 条 上下文工程 |

---

## 二、三条否决项（缺一不可）

这三条不是"加分项"，是**资格线**——缺任何一条，无论别的做得多好，都只能叫 Demo：

1. **完整后端工程体系**（第 2 条）——API 分层、数据库、会话管理、日志、错误处理、并发。
2. **可观测性 + 自动化评测**（第 7、8 条）——没评测的项目无法证明自己有效，等于自己宣布"我觉得效果还不错"。
3. **真实业务闭环**（第 1 条）——能回答三问，尤其是第 ③ 问"Agent 介入后，效率 / 成本 / 成功率提升在哪"。

> 注意第 2 条常被误当成"次要项"。作者把它单列一节，它和"Agent 能力"是**平级的两根支柱**。
> 反过来，一个只有工程没有 Agent 能力的项目（纯 RAG 问答 + 完整后端）也不算合格，见第 5 条。

## 三、7 支柱审查（逐条给判定 + 证据）

每条给出 `✅ 达标 / ⚠️ 部分 / ❌ 缺失` 三档之一，**后面必须跟一句代码层证据**（文件路径、命中计数、关键函数名）。判定细则见 [references/rubric.md](references/rubric.md)。

| # | 支柱 | 达标的最低要求 | 常见伪达标 |
|---|---|---|---|
| 1 | **真实问题与业务闭环** | 能答三问，第③问有口径 | 只有质量指标（忠实度/准确率），无效率或成本对比 |
| 2 | **后端工程体系** | 服务分层 + 配置 + 异常 + 鉴权 + 日志 + 并发考虑 | "我有 FastAPI" 但所有逻辑在一个 `main.py` |
| 3 | **数据与会话持久化** | 用户 / 会话 / 消息 / 任务 / 工具调用记录可查，跨会话保留 | 只用内存字典或前端 state |
| 4 | **任务状态管理** | 长任务有状态机或 State 对象，可查询进度、可恢复 | 只有 HTTP loading 动画 |
| 5 | **真正的 Agent 能力** | 意图识别 / 任务规划 / 工具选择 / 状态追踪 / 失败重试 / 结果校验 六项里至少 4 项有实现 | 只是 `LLM → tool → 返回`；**或**工作流项目却没有显式状态与重试 |
| 6 | **上下文工程** | 5 类上下文（当前任务 / 会话 / 用户记忆 / 工具 / 全局知识）至少覆盖 3 类，且有裁剪或预算控制 | 把"保存聊天记录"当上下文工程 |
| 7 | **可观测性与评测** | Trace 或结构化日志表 + 自动评分 + 门槛 + 可回归 | 有人工"感觉还行"的 eval，5 个 case，无门槛 |

第 5 条的两个易错判断，必须按下面口径下结论：

- **多 Agent 不是越多越好。** 剪辑、表单填写、固定审批这类单链路场景，**用稳定 workflow 反而更可控**。所以"拆了 7 个 Agent"本身不加分。
- 反过来，**workflow 也不是免检**：静态 DAG 要能证明它体现了规划（显式分解步骤）、状态追踪（State 对象 / 进度可见）和失败重试（节点级兜底），否则它就是一个"套了 LLM 的流水线"。
- 该条要回答的是**"你能解释为什么选这个架构吗"**（第 10 条），而不是"你是不是自主智能体"。

## 四、11 条清单逐条打分

完整清单、判定问题、证据采集方式见 [references/rubric.md](references/rubric.md)。输出时用表：

```markdown
| # | 判据 | 判定 | 实测证据 |
|---|---|---|---|
| 1 | 真实业务问题 | ⚠️ 基本满足 | 三问能答①②；③只有质量指标，缺效率/成本对比 |
| 5 | 规划/工具/记忆/反思 | ❌ 缺 3/4 | `@tool` 0 命中、`bind_tools` 0 命中、规划 0、反思 0 |
```

**证据纪律**：

- 判定项来自**代码里能不能找到对应机制**，必须写命中计数或文件路径（`rg` / `Test-Path` / `git` 输出）。
- 定性项（如"反思弱"）单独标注为**定性判断**，不和实测项混在一列。
- 无法核实的写 `未验证`，不写推测。
- 严禁给"综合得分 78 分"这类没有校准依据的精确总分——用档位（Demo / 合格 / 优秀）与满足条数表达。

---

## 五、档位结论

| 档位 | 判定条件 |
|---|---|
| **Demo** | 命中任一 Demo 过滤器；或三条否决项缺任一；或 11 条满足 ≤ 3 条 |
| **合格** | 三条否决项全在；11 条满足 4–7 条；第 5 条至少"部分" |
| **优秀** | 三条否决项全在；11 条满足 ≥ 8 条；且第 5、6、7、8 条都不低于"部分"，其中第 8 条（评测体系）达标 |

"满足"= 判定为 ✅ 或 ✅✅；"部分"不计入满足条数，单独列出。

档位后面必须跟一句**定位句**，指出它现在是什么、差在哪根支柱上，例如：

> 这是一个工程体系 A 级、评测 A+ 级的 RAG 系统，但 Agent 能力支柱（第 5 条）是空的。

## 六、输出格式

按 [references/report-template.md](references/report-template.md) 生成，固定结构：

1. **判定摘要**：档位 + 三条否决项是否通过 + 一句定位句
2. **30 秒过滤器结果**
3. **7 支柱表**（判定 + 证据）
4. **11 条清单表**（判定 + 实测证据）
5. **矛盾清单**：README / 简历声称 vs 代码实际（这条最容易被面试官抓住）
6. **行动清单**：按 A 直接命中清单 / B 补支柱 / C 把已有资产变成分数 / D 与标准无关但仍是硬伤 四类分组，每条标明命中第几条判据
7. **诚实边界**：哪些是实测、哪些是定性、哪些未验证
8. **三问自测表**（面试必备）：① 解决谁的问题 ② 原来怎么解决 ③ 提升在哪

行动项要写**投入产出**，优先"改动小、直接命中清单条目"的：

- 例：两个项目补结构化日志（请求 → 模型调用 → 工具调用 → 异常 → 耗时 → token）→ 命中第 2、7 条；
- 例：把已有架构选型理由写进 README/简历 → 不加功能，直接把第 10 条从扣分项变成加分项。

## 七、与其他 Skills 配合

- 审查结论要落成简历条目 → `/resume-writing`
- 审查暴露的问题要变成面试预测与追问 → `/interview`
- 补完工程后想删掉过度设计 → `/ponytail-audit`

推荐链路：

```text
/agent-project-review → 补 A/B 类行动项 → /resume-writing → /interview
```

审查报告写给**项目负责人自己**，用于决定改什么；简历只写经得起追问的部分。
