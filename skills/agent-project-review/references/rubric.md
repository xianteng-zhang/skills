# 判据原文与判定细则

内容：《一个好的 agent 项目的特征》共 9 节（7 节正文 + 结语）。以下为原文口径摘要 + 可执行判定标准。

---

## 一、原文七节

### 一、先解决真实问题，而不是为了 Agent 而 Agent

好的 Agent 项目一定要有明确场景。比如智能客服、代码修复、简历优化、数据分析、旅行规划、企业知识库问答、多部门审批流协同，都属于具体问题。它们有明确用户、有输入输出、有业务流程，也能衡量效果。

差的项目通常长这样：

- 用户输入一句话，模型回答一句话；
- 加几个工具调用，看起来像 Agent；
- 页面做得很炫，但业务闭环不存在。

**这种项目更像技术展示，而不是产品系统。**

真正好的项目要能回答三个问题：

1. 它解决谁的问题？
2. 原来这个问题怎么解决？
3. Agent 介入后，效率、成本或成功率提升在哪里？

> 如果这三个问题说不清，项目再复杂也只是包装。

### 二、必须有完整的后端工程体系

很多 AI 项目最大的问题，是只关注模型，不关注系统。但在企业环境里，Agent 本质上仍然是一个应用系统。它需要：API 服务、数据库、用户体系、会话管理、任务状态、日志、异常处理、权限控制、限流、超时重试和兜底策略。

一个能写进简历的 Agent 项目，至少应该体现这些能力：

- **API 服务层**：提供清晰的接口，而不是把逻辑全部写在一个脚本里。
- **数据库设计**：保存用户、会话、任务、工具调用记录、执行结果。
- **会话管理**：支持多轮任务，而不是只处理单次输入。
- **日志系统**：能追踪每次请求、模型调用、工具调用和异常。
- **错误处理**：模型超时、工具失败、接口异常时有兜底逻辑。
- **并发能力**：不是只能本地单人演示，而是考虑多用户使用。

> 如果一个项目只有 Prompt 和调用链，没有工程系统，面试官很容易判断它只是 Demo。

### 三、不能只是简单调用框架，要体现真正的 Agent 能力

很多所谓 Agent 项目，本质是：`用户输入 → 大模型 → 工具调用 → 返回结果`。这个流程没错，但它太薄了。**它没有体现规划、拆解、协作、记忆、纠错和状态管理。**

真正有含金量的 Agent 项目，应该体现以下能力：

- **意图识别**：先判断用户到底想做什么。
- **任务规划**：把复杂目标拆成多个可执行步骤。
- **工具选择**：根据任务选择搜索、数据库、代码执行、文件处理等工具。
- **状态追踪**：记录每一步执行到了哪里。
- **失败重试**：工具失败后可以换路径，而不是直接报错。
- **结果校验**：对最终输出做检查，而不是模型说什么就返回什么。

多 Agent 架构是一个很好的展示方式。例如一个旅行规划 Agent 可以拆成：主规划 Agent（理解目标、拆分任务）、信息查询 Agent（航班、酒店、天气、景点）、行程规划 Agent（生成路线）、预算 Agent（控制成本）、总结 Agent（输出最终方案）。

> **但要注意，多 Agent 不是越多越好。** 像剪辑 Agent、表单填写 Agent、固定审批 Agent 这类单链路场景，**用稳定 workflow 反而更可控**。好的架构不是炫技，而是匹配业务。

### 四、必须重视上下文工程

很多项目把上下文理解成"保存聊天记录"，这远远不够。在复杂 Agent 系统里，上下文是一项工程问题。**模型不应该看到所有历史信息，而应该看到当前任务真正需要的信息。**

上下文设计不好会出现：无关信息太多、模型判断能力下降；历史对话混乱、任务状态丢失；多 Agent 之间共享信息失控；用户长期偏好无法沉淀；每次都靠重新提示、系统不稳定。

一个好的 Agent 项目应该区分几类上下文：

- **当前任务上下文**：本轮任务目标、约束、输入数据。
- **会话上下文**：当前对话中的关键结论。
- **用户记忆**：用户偏好、历史选择、长期信息。
- **工具上下文**：工具返回结果、执行状态、错误信息。
- **全局知识上下文**：知识库、文档、业务规则。

> 这是面试里很容易被追问的地方。因为上下文工程决定了 Agent 能不能从"会聊天"走向"会做事"。

### 五、要有可观测性和评测体系

一个成熟的 Agent 项目，不能只靠"我觉得效果还不错"来判断质量。企业环境中，Agent 必须能被监控、追踪和评估。

你至少应该知道：

- 每次请求调用了哪些 Agent？
- 每次调用用了哪个模型？
- 工具调用是否成功？
- 失败发生在哪一步？
- 平均响应时间是多少？
- Token 成本是多少？
- 用户是否接受最终结果？
- 输出结果准确率如何？

可以接入 Langfuse 这类可观测平台，通过 Trace、Session、User 等维度记录系统行为；也可以自己设计日志表，记录模型输入输出、工具调用、任务状态和错误信息。

评测体系也很重要。比如对 Agent 输出结果做自动评分，从准确性、完整性、相关性、可执行性几个维度评分；对于 RAG 类项目，还可以评估召回率、引用准确性和幻觉率。

> 一个项目如果能展示"如何持续优化 Agent 效果"，它的含金量会明显高于普通 Demo。

### 六、要有人机协同，而不是盲目全自动

好的 Agent 不是所有事情都自动做到底。在关键节点上，它应该主动让人确认。比如：

- 删除文件前要确认。
- 发送邮件前要确认。
- 提交审批前要确认。
- 涉及资金、合同、隐私数据时要确认。
- 高风险操作失败后要转人工。

这类 Human-in-the-loop 设计，体现的是系统安全性和产品意识。

> **企业真正关心的不是 Agent 多聪明，而是它能不能可控地完成任务。**

### 七、判断标准清单

- 是否解决真实业务问题？
- 是否有完整后端架构？
- 是否有数据库和会话持久化？
- 是否有任务状态管理？
- 是否体现规划、工具、记忆和反思能力？
- 是否有上下文工程设计？
- 是否有可观测性和日志追踪？
- 是否有自动化评测体系？
- 是否有人机协同机制？
- 是否能解释为什么选择这个架构？
- 是否能量化项目收益？

> 如果这些问题大部分都能回答清楚，这个 Agent 项目就不只是 Demo，而是一个真正有简历价值的系统项目。

### 结语

好的 Agent 项目，不是"大模型 + Prompt + 页面"。它应该是一个围绕真实问题构建的智能应用系统：有业务闭环，有工程可靠性，有任务规划能力，有上下文管理，有监控评测，也有必要的人工干预。

> 面试官真正想看到的不是你会不会调用某个大模型，而是你有没有构建一个不确定的 AI 能力之上的确定性的工程系统。

## 二、11 条判据的判定细则

| # | 判据 | 达标问题（缺一即降级） | 采集证据 |
|---|---|---|---|
| 1 | 真实业务问题 | 三问全可答；第③问有 baseline 与口径 | README 的场景节 + 有无 baseline 数据 |
| 2 | 完整后端架构 | 有服务分层（router/service/repo 或等价）、配置层、异常层、鉴权、日志、并发说明 | 目录树 + 各层文件数 |
| 3 | 数据库和会话持久化 | 有表/集合定义；会话与消息落库；跨登录保留 | models/migrations/schema 文件 |
| 4 | 任务状态管理 | 长任务有状态字段或 State 对象；可查询进度 | 状态枚举 / `State` / 进度接口 |
| 5 | 规划·工具·记忆·反思 | 六项能力（意图/规划/工具选择/状态追踪/失败重试/结果校验）≥4 项有实现 | 工具注册表、planner、retry、critic |
| 6 | 上下文工程设计 | 5 类上下文 ≥3 类；有裁剪或 token 预算 | 记忆模块、摘要、裁剪函数 |
| 7 | 可观测性和日志追踪 | 有 Trace/结构化日志；8 问至少答得上 5 问（含 token 成本、失败位置） | logger 命中、日志表、Langfuse 痕迹 |
| 8 | 自动化评测体系 | 金标语料 + 门槛 + 可退出码/CI + 失败归因 | eval 脚本 + 数据集 + CI 配置 |
| 9 | 人机协同机制 | 高风险动作前确认；失败可转人工 | `interrupt` / `checkpoint` / 确认接口 |
| 10 | 能解释架构选择 | 写明为什么选它、替代方案是什么、为什么不选 | DESIGN.md / README 选型节 |
| 11 | 量化项目收益 | 质量收益 + 业务收益（人力/成本/风险），有口径 | 评测报告 + 业务换算 |

### 第 8 条的分级（最容易虚高）

| 等级 | 特征 |
|---|---|
| ❌ 不算体系 | 几个 case、人工跑、无门槛、不在 CI |
| ⚠️ 雏形 | 有金标集与脚本，但无门槛/无退出码 |
| ✅ 达标 | 金标集 + 门槛化 + 退出码 + 可回归 |
| ✅✅ 优秀 | 上述 + 失败归因分类 + 故障注入 + 消融实验 |

### 第 5 条的分级（区分"看起来像 Agent"和"真的是"）

| 等级 | 特征 |
|---|---|
| ❌ | 只有 `LLM → tool → 返回`，无状态、无重试、无校验 |
| ⚠️ | 有工具选择 + 状态追踪，但无规划或重试 |
| ✅ | 规划 + 工具 + 记忆 + 状态追踪齐全 |
| ✅✅ | 上述 + 失败重试换路径 + 结果校验/自评 |

### 工作流（workflow / 静态 DAG）项目的专门口径

不要因为"不是自主多智能体"扣分，也不要因为"有 7 个节点"加分。按这两问判：

1. **节点划分有没有业务依据？** 评估维度是否必须固定、可审计（是 → workflow 正确）。
2. **它是否具备工程化的状态管理？** State 对象、节点级重试、进度可见、失败可定位。

两问都"是" → 第 4、5 条可判 ✅；两问都答不上 → 第 5 条判 ❌，因为它是"套了 LLM 的流水线"。

## 三、矛盾检查表（面试官最爱抓的点）

逐条核对"声称 vs 实际"：

- README 说"N 个 Agent"，代码里是几个？
- 简历/README 说"支持多用户/并发"，有没有鉴权与限流？
- 说"有评测"，评测是否在 CI 跑、有无门槛？
- 说"生产级/上线"，有没有日志、灰度、回滚、监控？
- 说"提升 X%"，X 的 baseline、样本量、口径在哪？
- 说"记忆"，是长期偏好沉淀还是只是把历史拼进 Prompt？

任一条对不上，写进报告的矛盾清单——**这类问题在面试中的杀伤力远大于功能缺失**。

## 四、诚实边界（写进每份报告）

1. 本标准的原文来自图文，个别段落（可观测性页中间）有 UI 遮挡，不影响判据。
2. 实测项（grep 计数、文件存在性、git 状态）可靠；定性项（如"反思弱""闭环弱"）依据是"代码里能不能找到对应机制"，不是运行时实测。
3. 未跑过的评测/压测，只审方法论，不替它背书数字。
4. 人机协同要给"半个"的中间档：低风险的澄清追问算 HITL 雏形，但高风险确认与转人工才是完整项。
